NodeLite / SWE-smith Resource Transition Benchmark Checklist
==============================================================================
目标：为 Task-Resource Graph 的 edge weight 提供真实测量数据。
原则：测的是“从资源状态 A 切到 B 的实际代价”，不仅是软件名称是否相同。
数据基础：js ts benchmark任务统计(3).xlsx 的 84 项软件 + CTDP 已有 dependency/CAS 设计 + 为调度补充的环境状态资源。

优先级定义：
  P0 = 必测：有独立进程/daemon、明显冷启动、重要缓存/状态、或版本切换会造成显著失效。
  P1 = 建议测：主要是 cache/native artifact/toolchain/命令级切换；可能影响 invalidation cost。
  P2 = 不单独测“重启”：纯库/无独立进程；记录版本即可，成本跟随 Node/浏览器/数据库父资源。

每个 P0/P1 Resource 至少记录以下字段：
  - exact_version / compatibility_key
  - cold_start_ms（完全冷状态）
  - warm_start_or_attach_ms（已有 binary/cache/process 时）
  - switch_ms（同类不同版本 A→B）
  - reset_ms / cleanup_ms（Task A 结束后恢复可安全复用状态）
  - invalidation_ms（版本/ABI/config 变化导致 dependency/build cache 失效后的代价）
  - ready_ms（启动后真正可服务的时间）
  - rss_mb / peak_rss_mb
  - disk_bytes / cache_bytes
  - network_bytes_on_cold / network_bytes_on_warm
  - can_persist_across_tasks
  - reset_method
  - isolation_or_pollution_test
  - evidence/source

特别要同时记录的兼容维度：Node ABI、OS/arch/libc、PM版本、repo@commit、lockfile hash、config hash。

08. Electron（binary + app process）
09. Xvfb + D-Bus

11. SQLite（baseline DB file + reset）
12. canvas / sharp / SWC / esbuild / Prisma engine / node-gyp output（native ABI artifact）
13. Ubuntu/Debian rootfs + libc + arch + system toolchain bundle

16. Network namespace/ports reset

[D] 不要误算进 edge 的项目
------------------------------------------------------------------------------
1. 纯 JS 库（axios、Redux、Zod、GraphQL、Mongoose、Sequelize、TypeORM、Zustand 等）没有独立进程，通常不要给独立 restart weight。
2. Node 20→22 的 executable 选择本身通常很便宜；真正昂贵的是它导致 native addon / dependency view / build cache 失效，所以 weight 应主要记在被失效的 Resource 上。
3. 已全局共享、所有 CPU node 都可等价命中的 Raw CAS/rootfs/binary，不应因为“两个 Task 都用它”就重复给很大调度收益；只有 node-local warm state 或会被切换/失效的状态才强影响顺序。
4. task-private 源码、HOME/tmp、DB写数据、BrowserContext/profile 通常不是“复用收益”，而是 CleanupCost / RiskPenalty。

[E] 推荐最终 transition cost 分解
------------------------------------------------------------------------------
TransitionCost(A->B) = SwitchCost + ResetCost + ReloadCost + InvalidationCost + CleanupCost + RiskPenalty
ReuseBenefit(A->B) = ColdCost(B) - TransitionCost(A->B)
第一版 greedy scheduler 直接选择 ReuseBenefit 最大且安全约束满足的下一 Task/Profile。
